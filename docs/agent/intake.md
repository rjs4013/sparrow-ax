# 접수 규칙

사용하는 채널은 **프롬프트**와 **문서**다. 이슈 시스템은 쓰지 않는다(필요해지면 그때 추가한다).

## 접수 5단계
1. **원천 고정** — 지시의 원문을 확보하고 그 시점을 고정한다 (아래 채널별 규칙).
2. **분류** — 작업 유형(신규 구축 / 기능 추가 / 결함 수정 / 변경 / 문서 작업)을 정하고 경로를 제안한다.
3. **지시서 작성** — 경로에 비례하는 깊이로 쓴다.
4. **준비도 판정** — 수용 기준이 확인 가능한가, 결함이면 재현 절차가 있는가, 범위 경계가 분명한가. 부족하면 `AskUserQuestion`으로 묻는다. 모호한 항목은 **해석 후보를 2~3개 만들어 선택지로** 제시한다.
5. **분할** — 요구 항목이 여럿이면 지시서를 나누고, 공통 기반 작업과 의존 순서를 정해 사람의 승인을 받는다.

## 지시서 깊이

| 경로 | 지시서 |
|---|---|
| `quick` | 3줄(요청 · 가정 · 확인 방법). 파일로 남기지 않는다 |
| `fix` · `manual` | 간소형: 출처 · 증상/의도 · 수용 기준 · 산출물 목록 |
| `full` · `docs` | 전체형 (`worklog/` 파일, 형식은 `delivery.md`) |

## 채널별 규칙

| | 프롬프트 | 문서 |
|---|---|---|
| **원천 고정** | 원문을 지시서에 그대로 복사 | 경로 + 버전(`git hash-object <파일>` 값). 작업 중 문서가 바뀌면 멈추고 알린다 |
| **ID** | `WO-{YYYYMMDD}-{순번 2자리}` | 문서에 항목 ID가 없다. 임시 ID를 `TMP-{문서코드}-{n}`으로 붙이고 추적표에 출처 위치(절 번호)를 적는다. 문서코드: `C` = 경쟁사 계약·납품 문서, `B` = 입찰공고·낙찰 문서 |
| **경로 초기값** | 에이전트 판단 | 항목별로 판단. 신규 기능 → `full`, 문서 정정 → `docs` |
| **모호할 때** | `AskUserQuestion`으로 즉시 질문 (해석 후보를 선택지로) | 대화 상대가 문서 소유자이거나 답할 권한이 있으면 `AskUserQuestion`. 아니면 질문 목록(질문 + 선택지)을 만들어 문서 소유자에게 전달. **원본 문서는 고치지 않는다** |
| **특유의 위험** | 기록이 남지 않음 → 지시서가 유일한 기록 | 표 · 그림 · 메모의 누락 → 읽지 못한 부분을 명시 |

## 문서 채널 세부
- 요구 항목은 **원문 문장을 인용해** 추출한다. 요약하면서 의미를 바꾸지 않는다.
- 항목 사이의 모순, 누락된 수용 기준, 기존 시스템과의 충돌을 목록으로 만들어 구현 전에 돌려보낸다. 이미 알려진 목록은 `ARCHITECTURE.md`의 "함정"에 있다.
- **범위 밖으로 결정된 항목**(예: SP영업 메일 알림)은 추출하되 상태를 `범위 밖`으로 표시하고 구현하지 않는다.
- 임시 ID는 문서 소유자가 정식 ID를 부여하면 추적표에서 교체한다.
- 이 저장소의 요구사항 문서는 모두 Markdown이라 변환 손실은 없다. 다른 형식(docx 등)이 들어오면 변환 중 빠진 요소를 지시서의 "읽지 못한 것"에 적는다.

## 채널이 겹칠 때
- "이 문서대로 하되 3장은 빼고"처럼 프롬프트가 문서를 **가리키거나 범위를 줄이는** 경우: 내용은 문서에서, 범위는 프롬프트에서 가져온다.
- 채널 사이에 **내용이 상충**하면 조용히 한쪽을 고르지 않는다. 상충 지점을 제시하고 묻는다.
- 무인 실행 중이라 물을 수 없으면 멈추고 차단 사유를 남긴다. (현재 무인 실행은 구성하지 않았다)
