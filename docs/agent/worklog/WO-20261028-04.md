계산으로 확인한 사실 (`node`로 입력 파일을 파싱): 제조사별 번호 수는 스패로우 24(메모의 추가 2개 포함), 에스에스알/트리니티소프트 9, 정보라인/이븐스타 10, 나일소프트 6, 코드마인드 5, 코드원 2, 싸이버텍 2, 래브라도랩스 1, 하로스 1. 제공자가 대조 필요라고 한 7개 중 `23585469` · `23585470`(스패로우)과 `24003938`(정보라인)은 목록 안에서 한 곳에만 나오고, 나머지 4개가 위 충돌 번호다(`22849502`는 3개 제조사).

#### 가정 (틀리면 알려 달라)
- **결정 9 해석:** 대상은 문서 3.1의 9개사(스패로우, 에스에스알, 정보라인, 코드마인드, 하로스, 나일소프트, 레드펜소프트, 코드원, 래브라도랩스)에 **트리니티소프트를 포함**한다고 읽었다. 제외하겠다고 명시한 것은 세 곳뿐이라서다. 트리니티소프트는 목록상 "에스에스알 / 트리니티소프트"로 묶여 있어 에스에스알의 **별칭**으로 취급하며, 동일 법인이라는 사람의 확인이 필요하다(제공자도 확인 필요라고 적음).
- **이븐스타 제외의 효과:** 계약의 업체명이 "이븐스타"인 건은 수집하지 않는다. 같은 묶음의 식별번호 10개는 정보라인 항목으로 그대로 보관한다.
- **파수닷컴 제외의 효과:** 계약의 업체명이 "파수닷컴"인 건은 수집하지 않는다. 그 명의로 계약된 구형 SPARROW 4개(`22564613` · `22564614` · `22567280` · `22568215`)의 과거 실적은 잡히지 않는다. 의도한 것인지 확인이 필요하다.
- **싸이버텍 제외의 효과:** 식별번호 2개(`22835795` · `22835796`)는 저장하지 않는다.
- **레드펜소프트:** 문서 3.1에는 있지만 받은 목록에 식별번호가 없다. 업체명 기준 수집은 그대로 하고 식별번호 매칭만 비어 있다.
- **결정 5 보강:** 식별번호 목록이 생겼으므로 "분류번호 + 업체명이 일치하는 건은 모두 저장하고, 식별번호가 목록과 일치하는 건은 **'확인 대상' 표시**"로 구현한다. 목록에 없는 신제품도 놓치지 않는다.
- 식별번호 목록은 설정 파일(제조사 → 번호 → 제품명)로 두고, 입력 1의 원문을 기반으로 하되 제외된 업체의 번호는 넣지 않는다.

### 사람이 준비할 것 (구현 시작 조건)
1. ~~보안SW 물품분류번호~~ → 받음 (`4323320501`)
2. **트리니티소프트 = 에스에스알 동일 법인 여부 확인**, 그리고 문서 3.1 · 9.2에 트리니티소프트를 반영할지 결정(반영하려면 `docs` 작업). 파수닷컴 제외가 의도한 것인지 확인.
3. 공공데이터포털에서 **조달청 OpenAPI 서비스키 발급**과, 납품요구 조회에 쓸 **서비스명 · 엔드포인트 확인**. 키는 `.env`의 `G2B_SERVICE_KEY`에 Decoding(원문) 키로 넣는다. 대화나 기록에 붙여 넣지 않는다. 이 키가 있어야 **등록 상호 후보 확정**(결정 11)과 **고유 키 승인**(결정 4)도 진행된다.
4. API 응답 필드를 본 뒤 **고유 키 조합 승인** (결정 4)
5. 충돌 식별번호 4개의 원본 대조(결정 10, 구현을 막지는 않음)

**서비스키 없이 먼저 구현 가능한 것:** 분류번호 필터(`4323320501` 정확 일치), 업체명 정확 일치 필터, 식별번호 '확인 대상' 매칭, 수집 기간 계산(마지막 성공일 이후)은 샘플 입력으로 구현하고 테스트할 수 있다. 저장 테이블과 실제 API 호출은 서비스키 · 응답 필드 확인 뒤에 한다.
