## 날짜 기준 문제: 이 문서에서 가장 중요한 불일치

| 구분 | 내용 |
|---|---|
| 요구사항 | "전일자와 납품요구일자가 일치하는 건"을 신규로 본다 (경쟁사 §4.1 · 7.1). 구현한 `collectionRange`와 결정 12(첫 실행은 올해 1월 1일부터)도 이 **납품요구일자 범위**를 전제한다 |
| 명세 [원문] | 물품 기본 · 세부 조회의 검색조건은 "**등록일시**, 통합계약번호 **등**"이다. 나라장터 검색조건에 따른 `PPSSrch`는 "계약체결일자, 확정계약번호, … 계약참조번호"다 |
| 불일치 | (1) 응답에 납품요구일자가 없고 계약체결일자가 있다. (2) 기본 · 세부 조회로 검색할 수 있다고 **확인된** 날짜는 등록일시다. 늦게 등록된 계약은 등록일시와 계약체결일자가 다를 수 있다 [추론] |
| 확인 안 된 것 | 기본 · 세부 조회에 계약체결일자 검색조건이 있는지는 "등"에 가려져 **알 수 없다.** `PPSSrch`로 계약체결일자를 검색하더라도 세부 조회(분류번호 · 식별번호)는 별도로 불러야 한다 |
| 날짜 축 후보 경로 | [원문] 개방표준서비스의 계약정보 `getDataSetOpnStdCntrctInfo`는 검색조건이 **"계약체결일자로"로 닫혀 있고**(등 없음) 응답에 통합계약번호 · 계약체결일자가 나열되어 있다. [추론] 계약체결일자로 하루치 계약을 열거하고 `통합계약번호`로 계약정보서비스의 세부 조회와 잇는 경로가 가능해 보인다. 응답에 업체 · 수요기관이 있는지는 미확인이라 경쟁사 수집을 이 오퍼레이션만으로 하지는 못할 수 있다. 결정 14의 제안 근거 후보다 |
| 쇼핑몰 납품요구 건 | [일반지식, 원문에 근거 없음] 나라장터에서 "납품요구"는 종합쇼핑몰 구매에서 쓰는 용어다. 쇼핑몰 납품요구 건이 이 서비스의 물품 계약으로 조회되는지, `계약구분` 값으로 구별되는지는 **확인되지 않았다.** 이 서비스에 포함되지 않는다면 다른 서비스를 추가 신청해야 한다 |

## 이 구조가 구현에 주는 영향 (모두 [추론], 응답 확인 전)
1. **업체와 분류번호가 서로 다른 오퍼레이션에 있다.** `통합계약번호`로 잇는다. [원문] 열거된 검색조건에 업체 · 분류번호는 없지만 "등"으로 끝나 서버 쪽 검색조건이 **없다고는 단정할 수 없다.** 있다면 호출이 크게 줄어든다.
   - 서버 필터가 없다면: 하루치 기본 조회를 받아 **업체명 정확 일치**로 먼저 줄이고, 남은 계약만 세부 조회해 **분류번호 `4323320501`** 을 확인하는 순서가 가능하다.
   - 이 순서가 최종 결과를 바꾸지 않는 전제: 두 조건이 AND이고 업체정보가 계약 단위로 있다. 호출 수가 줄어드는 정도는 세부 조회가 계약별로만 가능한지(등록일시 일괄 조회가 가능하면 이득이 다르다)에 달려 있어 **정량 근거가 없다.**
   - **위험:** 업체정보 파싱이 틀리면 대상 계약이 세부 조회 전에 사라진다. 파싱은 실제 응답으로 검증하고, 실패한 건은 버리지 말고 기록한다.
   - **코드 영향:** 현재 `classify()`는 분류번호 · 업체명 · 식별번호가 모두 든 한 레코드를 받아 분류번호 → 업체명 순으로 판정한다. 호출 순서를 바꾸려면 업체 단독 판별 함수가 필요하고 거부 사유(`category` 우선)도 달라진다. 구현 시점에 `src/filters/contracts.ts`를 조정한다.
2. **일일 트래픽이 작다.** [원문] 계약정보서비스는 상세기능마다 1000이며 이는 **개발계정 기준**이다. 오퍼레이션별로 따로 센다. 하루 계약 건수와 페이지 크기 상한을 모르므로 호출량은 계산할 수 없다. 필요한 계산식은 두 개다. **기본 조회:** `일수 × 하루 페이지 수 ≤ 1000`, **세부 조회:** `세부 호출 수 ≤ 1000`(각자 따로 센다). 결정 12의 약 300일 백필(1/1~10/27은 300일)이 한도 안에 들어오는지는 건수를 본 뒤 정한다. 안 되면 여러 날에 나눠 처리하고, 운영계정 전환 · 한도 상향 신청도 방법이 될 수 있다 [일반지식, 원문에 근거 없음].
3. **고유 키 후보(결정 4).** `통합계약번호` + `물품식별번호`가 후보이나 한 계약에 같은 식별번호가 여러 줄이면 구별이 안 된다. [원문] 세부 응답에는 순번 · 행번호 필드가 없다(닫힌 목록). 순번을 응답 순서에서 만들면 불안정하다. 대체 후보는 `확정계약번호`, `계약참조번호`이고 실제 응답으로 정한다.
4. **변경 · 삭제 이력 오퍼레이션**(`ChgHstry`, `DltHstry`)은 [원문] 이름과 검색조건(변경일시 · 삭제일시, 통합계약번호)이 확인된다. 응답 필드는 input.md의 [에이전트 요약]에만 있다. [추론] 이미 저장한 건의 정정 · 삭제를 반영하는 데 쓸 수 있을 것으로 보인다. 요구사항에 없어 이번 범위 밖이고 필요해지면 별도 지시서로 정한다.

## 확인 방법과 사람이 할 일
1. **활용가이드(Excel · Word 명세서)** 가 포털에 있다면 내려받아 응답 · 요청 필드 **전체 목록**을 확인한다. "등"으로 끝난 목록이 해소될 수 있다 [일반지식: 활용가이드가 있고 전체 필드를 담고 있다는 것은 발췌에 근거가 없다]. 가능하면 이것을 먼저 한다.
2. 실제 호출로 응답을 확인한다. 하루치만 호출하고 **필드 이름 · 값 형식 · 건수 · 쇼핑몰 건 포함 여부**만 출력하며 서비스키는 출력하지 않는다. 필요한 것: ① `.env`의 서비스키(Decoding) ② 서비스별 요청주소. 서비스가 둘(계약정보, 개방표준)이라 `G2B_BASE_URL` 하나로는 부족하다. 서비스별 URL을 따로 받도록 설정을 바꿀 것을 호출 확인 때 함께 제안한다.
3. 날짜 기준 중 14번(신규 판정 날짜)은 위 1 · 2의 결과를 보고 제안한다.
