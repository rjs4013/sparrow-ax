# WO-20261028-10 하이브리드 수집기: 매일 등록일시 증분 + 주 1회 교차 검증

## 지시서

- 요청자 / 실행자: rjs4013 / 메인 에이전트. 질문 · 환류 채널: 대화.
- 유형: 기능 추가. 경로: `full` (DB 구조 변경, 외부 API 호출 방식 추가).
- 요구 항목
  - W10-1 매일 증분: 결정 14 "이후 매일 수집은 등록일시 증분 + 체결일자 빈 행 폐기" → 수용 기준: 마지막 성공일 다음 날부터 어제까지를 **하루씩** 기본 조회(`getCntrctInfoListThng`, `inqryDiv=1`, 등록일시 `YYYYMMDD0000`~`YYYYMMDD2359`, 999건 페이지)로 받고, 체결일자가 빈 행을 버리고, 9개사 판정 → 세부 조회 분류번호 판정을 기존 로직으로 한다 / 확인: 가짜 클라이언트 테스트 + 승인된 실호출.
  - W10-2 하루 단위 저장 · 재개: "API 실패 시 3회 재시도 후 기록하고 중단(마지막 성공일 미갱신)"(결정 6, 인계 3절) → 수용 기준: 하루가 끝날 때마다 그 날 결과를 저장하고 그 날의 실행 기록(성공)을 남긴다. 중간에 실패하면 거기서 멈추고 실패를 기록하며, 다음 실행은 마지막 성공한 날 다음 날부터 이어 간다 / 확인: 테스트.
  - W10-3 교차 검증: 결정 14 "주 1회 체결일자 방식으로 교차 검증" → 수용 기준: 최근 N일(기본 14일, 최소 8일: 등록 지연 관측 최대 7일)을 체결일자 검색(기존 방식)으로 다시 받아, DB에 없던 9개사 계약 수를 실행 기록 메모에 남기고 저장한다. **"증분이 놓친 것"은 등록일이 증분의 마지막 성공일 이하인 것만 센다**(등록일이 아직 증분 차례 전인 계약은 놓친 것이 아니다. 검토에서 지적된 거짓 경보 방지) / 확인: 테스트.
  - W10-4 상태 표시: "잘 되고 있는지 확인" → 수용 기준: 화면이 백필 · 매일 · 교차 검증의 마지막 실행 상태를 각각 보여 준다 / 확인: 서버 주입 테스트 + 브라우저.
- 확인된 값 · 가정
  - 확인(WO-07 5차): 등록일시 하루 조회는 약 4,200건(999건 × 약 5쪽, 하루 약 7MB)이고 이 중 약 절반은 체결일자가 빈 사전 등록 중복 행이다. 기본 조회에는 서버 품명 필터가 없다. 기본 조회 행에도 `corpList` · `dminsttList`가 있다(저장해 둔 응답으로 확인).
  - 가정: 등록일시는 한국 시간이다(탐침에서 한국 날짜로 조회해 일치). "어제"까지만 받는다(오늘은 하루가 끝나지 않았다).
  - 가정: 증분의 시작점은 `daily` 성공 기록의 마지막 날 다음 날이다. 기록이 없으면 **가장 최근 백필 성공 실행이 시작된 한국 날짜**부터 시작한다(백필 이후에 등록되는 계약을 빠짐없이 받고 겹치는 구간은 upsert라 안전). 둘 다 없으면 백필을 먼저 하라는 오류로 멈춘다.
  - 가정: 기본 호출 상한은 증분 80회(하루 약 8회 × 밀린 일수 여유), 교차 검증 40회. 사람이 `--max-calls`로 바꿀 수 있고 상한은 1000.
  - 가정: 스케줄은 이번에 만들지 않는다(운영 환경 미정). 실행 명령 3개를 문서에 적고 사람이 작업 스케줄러에 건다. 새벽 6시 실행 시점은 등록 지연을 고려해 증분이 "어제"를 받는 것으로 충분하다(어제 등록분은 오늘 새벽에 모두 존재).
- 미해결 질문: DB 열 추가(아래)와 실호출 횟수의 사람 승인 — 구현 후 실행 전에 받는다.
- 범위 밖: 스케줄 등록, 엑셀, 입찰 · 낙찰, 삭제 · 재분류 반영(upsert만), 수요기관별 납품요구 소스 조사.

## 기록
- 변경 집합: 브랜치 `feat/WO-20261028-10-hybrid-collector` (WO-09 브랜치 위에서 분기, 커밋 1개). 사람이 실호출(약 25회)과 DB 열 추가(`0002_run_kind`)를 승인했다(2026-10-29, `AskUserQuestion`).
- 실호출 결과(승인된 범위 안, 합계 12회): ① `--mode daily --from 2026-10-27 --max-calls 40` → 등록일 10-27 4,214건(5쪽) · 10-28 3,593건(4쪽) 수신, 9개사 계약 0건 저장, 호출 9회, 하루 1행씩 `daily` 실행 기록 2개. 10-27의 4,214건은 WO-20261028-07 5차의 실측(4,214건)과 같다. ② `--mode verify --days 14 --max-calls 15` → 체결일자 10-15~10-28에서 22건 수신, 9개사 계약 2건 확인(이미 저장된 나일소프트 2건과 같은 것), 새로 찾은 계약 0건, 호출 3회. 로컬 DB의 기존 백필 행은 마이그레이션 후 `kind=backfill`이 되었고 계약은 11건 그대로다.
- **실호출로 확인하지 못한 것:** 증분이 9개사 계약을 실제로 찾아 세부 조회까지 가는 경로(이번 두 날짜에는 9개사 계약이 없었다 — 가짜 클라이언트 테스트로만 확인), 등록일시 구간 끝 `2359` 직후(23:59:xx) 등록분이 빠지는지(API가 분 단위로 자르는지 모름, 교차 검증이 체결일자 기준으로 일부 보완), 매일 증분의 하루 응답이 7MB 안팎인 점의 장기 운영 영향.
- 게이트: `bash scripts/gate.sh` → 종료코드 0, 건너뜀 없음. 검토 반영 후 최종 테스트는 아래 "최종 게이트" 줄.
- 검토: `reviewer`(별도 컨텍스트) 조건부 통과, 차단 없음, 중요 2건. 반영한 것: ① 교차 검증의 거짓 경보(체결일자는 과거인데 등록일이 아직 증분 차례 전인 계약을 "놓친 것"으로 세던 것) → 증분의 마지막 성공일 이하 등록분만 센다(테스트 추가), ② 낡은 문서 한 줄 정리, ③ 증분 시작점을 가장 늦은 `range_to` 기준으로(과거 구간 재수집이 시작점을 뒤로 돌리지 않음, 테스트 추가), ④ `--days` 하한 8, ⑤ 모드와 맞지 않는 옵션(`--to`, `--days`, `--from`)은 오류로 알림, ⑥ 받을 날이 없으면 실행 기록이 남지 않는다는 점과 밀린 구간 안내를 문서에 명시. **반영하지 않은 것:** 등록일시 종료 시각 `2359` 경계(실호출로만 확인 가능, 위 "확인하지 못한 것"), `main.ts` 명령 분기는 단위 테스트가 없고 코드 검토로만 확인(범위 밖 일이 아니라 입력 검증이 단순해서 두었다), 한국 날짜 경계(UTC 15시 전후) 테스트 없음(로직은 `todayKst` 재사용).
