# sparrow-ax 아키텍처

## 개요
스패로우 SP사업팀 · 영업 담당자를 위해 나라장터 데이터를 매일 수집하고 웹 View로 보여 주는 영업 지원 시스템이다.
요구사항은 **별도 View 두 개**(경쟁사 계약·납품 실적, 공공 입찰공고·낙찰)로 정의되어 있다.
**현재는 공통 기반만 있다**(스캐폴딩 WO-20261028-03). 수집 · 필터 · View 등 기능은 아직 구현되지 않았다.

## 기술 스택 (사람 승인, WO-20261028-03)
Node 24 + TypeScript(`tsc --noEmit`으로 타입 검사, 실행은 Node의 타입 제거), SQLite(`node:sqlite` 내장), Fastify, 테스트는 `node:test`.
아직 설치하지 않은 승인 항목: 엑셀 내보내기용 `exceljs`(엑셀 작업의 지시서에서 추가). 운영 환경은 미정이라 로컬 실행 기준이고 수집은 CLI 명령 + 외부 스케줄러로 붙일 예정이다.
코드는 `import type`과 `.ts` 확장자 import를 쓰고, 열거형 · 네임스페이스 등 타입 제거로 지워지지 않는 문법은 쓰지 않는다(`erasableSyntaxOnly`).

## 핵심 개념

| 기능 | 목적 | 입력 | 출력 | 핵심 기법 |
|---|---|---|---|---|
| 경쟁사 계약·납품 실적 모니터링 | 스패로우 · 경쟁사 8곳의 신규 계약·납품 탐지와 이력 조회 | 나라장터 계약·납품요구 데이터 (전일자 = 납품요구일자) | 누적 DB, 일/주/월 조회 View, 월 단위 엑셀 | 3단 필터: 물품분류번호(보안SW) → 업체명 → 물품식별번호 |

## 주요 진입점
- `src/db/index.ts`: `openDb(path)`는 SQLite를 열고(WAL, 외래키 켬), `migrate(db, list?)`는 미적용 마이그레이션만 id 순으로 트랜잭션 실행한다. 테이블 스키마는 `migrations` 배열에 `{ id: '0001_...', sql }`로 추가한다(현재 비어 있음).
- `src/g2b/client.ts`: `loadG2bConfig(env)`는 `G2B_SERVICE_KEY` · `G2B_BASE_URL`을 읽고, `createG2bClient(config, fetch?)`는 `buildUrl` · `get`을 제공한다. 서비스키는 오류 메시지에 남기지 않는다(호출 실패 · JSON 파싱 오류는 원문 · 인코딩 형태 모두 마스킹, 응답 오류에는 키 없는 URL 사용). 빈 키로는 클라이언트를 만들 수 없다. 포털의 Decoding(원문) 키를 쓴다. 리다이렉트 · 타임아웃 정책은 실호출 지시서에서 정한다. 서비스별 엔드포인트는 **미확정**이라 실호출 코드는 없다.
- `src/web/server.ts`: `buildServer()`는 Fastify 앱을 만든다(현재 `GET /health`만). `src/web/main.ts`는 DB 초기화 후 `HOST`(기본 127.0.0.1) · `PORT`(기본 3000)로 기동한다. 실행은 `npm start`.
- 환경변수는 `env.example` 참조(`.env`로 복사). 실행 명령: `npm run build` · `lint` · `test`, 전체 게이트는 `bash scripts/gate.sh`.

## 처리 흐름
- 경쟁사: 전일자 납품요구 조회 → [1차] 물품분류번호 → [2차] 업체명 → [3차] 물품식별번호 → 저장 → 웹 조회 → 엑셀 내보내기
- 입찰·낙찰: 전일자 신규 공고 조회 → 공고명 키워드 필터 → 저장 → 웹 조회 / 신규 낙찰 수집 → 기존 공고 매칭 또는 단독 저장 → 웹 조회

## 핵심 알고리즘 · 외부 의존
- 외부 데이터 원천: 나라장터. 호출 방식은 공공데이터포털 조달청 OpenAPI + 서비스키로 결정됐다. 서비스별 엔드포인트와 응답 형식은 **미확정**이다.
- 외부 LLM 호출 기능은 제품에 포함하지 않는다.

## 범위 결정 (사람이 내린 것)
- **SP영업 메일 알림 기능은 범위 밖이다** (2026-10-28 사용자 지시). 구현하지 않는다.
  경쟁사 문서에서는 WO-20261028-02로 해당 부분을 삭제했다(1.2, 시나리오 1, 6장 흐름, 7.1 처리 조건, 10장 요약표, 11장 확인 항목). 7.2는 다른 절 번호 유지를 위해 "(삭제)" 안내만 남겼다. 이후 문서 인용 시 11장의 마지막 항목(엑셀 파일명 및 출력 범위)은 8번이 아니라 7번이다.

## 확장 레시피
### 새 테이블 추가
1. `src/db/index.ts`의 `migrations`에 `{ id: '000N_설명', sql }`를 추가한다(이미 적용된 id는 수정하지 않는다).
2. `migrate`를 쓰는 테스트에 새 스키마를 검증하는 케이스를 추가한다.
3. 위험 신호 "DB 구조 변경"이 켜지므로 검토를 받는다.

"새 키워드 추가", "새 모니터링 대상 업체 추가" 같은 확장은 해당 기능이 구현되면 여기에 적는다.

## 함정
요구사항 문서에서 확인된 내부 불일치(구현 전에 사람에게 돌려보낼 목록):
1. (해소됨, WO-20261028-02) 경쟁사 문서의 메일 포함 정보 불일치는 메일 기능 삭제로 사라졌다.
2. 입찰 4.1은 "업무구분 · 추정가격 · 입찰마감일"을 쓰지만 수집 항목은 "기초금액 · 등록마감 · 투찰마감"이다.
3. 입찰 4.2는 "낙찰일자"를 확인한다고 쓰지만 낙찰정보 수집 항목에 낙찰일자가 없다.
4. 입찰 5.4의 추세 예시에 "AI", "개인정보"가 있으나 필터 키워드 15종에는 없다. (필터에 없는 공고는 저장되지 않으므로 추세 집계도 불가)
5. 경쟁사 11장의 미확정 항목(보안SW 분류번호 목록, 업체명 표기, 제품별 식별번호, 중복 방지 키, 수집 시간, 오류 처리)은 구현 전에 확정이 필요하다. 입찰 문서에도 공고↔낙찰 매칭 키 · 수집 시간 · 오류 처리 정의가 없다.
