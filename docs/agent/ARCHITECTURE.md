# sparrow-ax 아키텍처

## 개요
스패로우 SP사업팀 · 영업 담당자를 위해 나라장터 데이터를 매일 수집하고 웹 View로 보여 주는 영업 지원 시스템이다.
요구사항은 **별도 View 두 개**(경쟁사 계약·납품 실적, 공공 입찰공고·낙찰)로 정의되어 있다.
**현재는 공통 기반만 있다**(스캐폴딩 WO-20261028-03). 수집 · 필터 · View 등 기능은 아직 구현되지 않았다.

## 기술 스택 (사람 승인, WO-20261028-03)
Node 24 + TypeScript(`tsc --noEmit`으로 타입 검사, 실행은 Node의 타입 제거), SQLite(`node:sqlite` 내장), Fastify, 테스트는 `node:test`.
아직 설치하지 않은 승인 항목: 엑셀 내보내기용 `exceljs`(엑셀 작업의 지시서에서 추가). 운영 환경은 미정이라 로컬 실행 기준이고 수집은 CLI 명령 + 외부 스케줄러로 붙일 예정이다.
코드는 `import type`과 `.ts` 확장자 import를 쓰고, 열거형 · 네임스페이스 등 타입 제거로 지워지지 않는 문법은 쓰지 않는다(`erasableSyntaxOnly`).

## 주요 진입점
- `src/db/index.ts`: `openDb(path)`는 SQLite를 열고(WAL, 외래키 켬), `migrate(db, list?)`는 미적용 마이그레이션만 id 순으로 트랜잭션 실행한다. 테이블 스키마는 `migrations` 배열에 `{ id: '0001_...', sql }`로 추가한다(현재 비어 있음).
- `src/g2b/client.ts`: `loadG2bConfig(env)`는 `G2B_SERVICE_KEY` · `G2B_BASE_URL`을 읽고, `createG2bClient(config, fetch?)`는 `buildUrl` · `get`을 제공한다. 서비스키는 오류 메시지에 남기지 않는다(호출 실패 · JSON 파싱 오류는 원문 · 인코딩 형태 모두 마스킹, 응답 오류에는 키 없는 URL 사용). 빈 키로는 클라이언트를 만들 수 없다. 포털의 Decoding(원문) 키를 쓴다. 리다이렉트 · 타임아웃 정책은 실호출 지시서에서 정한다. 서비스별 엔드포인트는 **미확정**이라 실호출 코드는 없다.
- `src/web/server.ts`: `buildServer()`는 Fastify 앱을 만든다(현재 `GET /health`만). `src/web/main.ts`는 DB 초기화 후 `HOST`(기본 127.0.0.1) · `PORT`(기본 3000)로 기동한다. 실행은 `npm start`.
- `src/filters/contracts.ts` (경쟁사 계약 · 납품 필터, 순수 함수): `loadMonitoringConfig()`가 `config/contract-monitoring.json`을 읽어 `parseMonitoringConfig`로 엄격히 검증한다(분류번호 10자리, 식별번호 8자리, 업체 id · 상호 중복 거부). `createMatcher(config).classify(record)`는 1차 물품분류번호 정확 일치 → 2차 업체명 정확 일치(앞뒤 공백만 무시) 순으로 거르고, 통과한 건에 3차로 `verified`(식별번호가 그 업체의 확인 대상 목록에 있음)와 `idConflict`(여러 업체 목록에 걸친 번호라 원본 대조 필요)를 붙인다. 3차는 걸러내지 않으므로 목록에 없는 신제품도 통과한다. `conflictIds`는 현재 `22300118` · `22300119` · `22849502` · `22849503`이다.
- `src/filters/dates.ts`: 날짜는 `YYYY-MM-DD` 문자열. `collectionRange(lastSuccess, today)`는 수집할 납품요구일자 범위를 돌려준다(마지막 성공일 다음 날 ~ 어제, 첫 실행은 올해 1월 1일 ~ 어제, 수집할 날이 없으면 `null`, 마지막 성공일이 오늘보다 미래면 오류). `eachDay`는 일 단위로 나눠 API 일일 한도를 지키기 위한 것이고, `todayKst`는 한국 시간 기준 오늘이다.
- `config/contract-monitoring.json`: 분류번호, 9개사(상호 · 잠정 여부 · 확인 대상 식별번호 58개). `provisional: true`인 업체의 상호는 나라장터 등록 상호를 확인하지 못한 잠정 표기라 **서비스키 발급 후 수집 데이터로 확정해야 한다**(정확 일치라 틀리면 놓친다). 원문 출처는 `docs/agent/worklog/WO-20261028-04-input-1.md`.
- 환경변수는 `env.example` 참조(`.env`로 복사). 실행 명령: `npm run build` · `lint` · `test`, 전체 게이트는 `bash scripts/gate.sh`.

## 처리 흐름
- 경쟁사: 수집 범위 계산(마지막 성공일 다음 날 ~ 어제, 일 단위 호출) → 납품요구 조회 → [1차] 물품분류번호 → [2차] 업체명 → [3차] 물품식별번호 '확인 대상' 표시 → 저장 → 웹 조회 → 엑셀 내보내기. (구현 상태: 범위 계산과 3단 필터까지. 조회 · 저장 · View는 아직 없음)
- 입찰·낙찰: 전일자 신규 공고 조회 → 공고명 키워드 필터 → 저장 → 웹 조회 / 신규 낙찰 수집 → 기존 공고 매칭 또는 단독 저장 → 웹 조회

## 핵심 알고리즘 · 외부 의존
- 외부 데이터 원천: 나라장터. 호출 방식은 공공데이터포털 조달청 OpenAPI + 서비스키로 결정됐다. 활용신청한 3개 서비스 중 **잠정 선정**(WO-20261028-05, 실제 호출 전의 가설): 경쟁사 수집은 **계약정보서비스**(물품 계약 `getCntrctInfoListThng` + 물품 세부 `getCntrctInfoListThngDetail`, 둘은 통합계약번호로 연결), 입찰 · 낙찰은 **공공데이터개방표준서비스**(입찰공고 · 낙찰, **잠정**: 필요한 필드가 있는지 미확인이라 부족하면 서비스를 추가 신청해야 할 수 있다), 공공조달통계정보서비스는 집계 통계로 보여 쓰지 않는 것으로 본다. 일일 트래픽은 개발계정 기준으로 계약정보서비스가 오퍼레이션당 1000회, 개방표준서비스가 10000회다.
- **활용가이드로 확인된 것(WO-20261028-06):** 가이드의 요청 · 응답 **명세 표**를 확인했다(원문 발췌는 WO-20261028-06-input.md). 단 계약정보 기본 · `PPSSrch`의 예제 응답에는 명세 표에 없는 요소 5개와 대소문자 차이가 있어 응답 파서는 키를 대소문자 무시로 읽어야 한다. 서비스키는 쿼리스트링으로 전달되고, 가이드는 주소를 `http://apis.data.go.kr/1230000/ao/CntrctInfoService`, `…/PubDataOpnStdService`로 적고 전송 암호화를 "없음"으로 표기한다. 사용자의 `.env` 설정은 같은 주소를 **https**로 쓰고 있고(가이드 값이 아니라 사용자 설정) **https로 정상 응답함을 호출로 확인했다**(WO-20261028-07). 서비스키 이름은 `ServiceKey`와 `serviceKey` 둘 다 계약정보서비스에서 같은 응답이 왔다(개방표준은 대문자만 확인). 실측 규모: 계약 `PPSSrch` 하루 약 1300건, 입찰공고 하루 약 1970건, 낙찰(물품) 하루 약 16000행(투찰업체별 행). **계약체결 다음 날 오전에 등록되는 계약이 있음을 확인했다**(표본 1건). 세부 조회의 분류번호 · 식별번호는 8자리로 확인했다. 물품 계약 `PPSSrch`는 **계약체결일자**로 검색할 수 있고, 기본 · 세부 조회는 등록일시 또는 통합계약번호로만 검색한다. `업체목록` · `수요기관목록`은 `^`로 구분된 구조화 문자열이며 업체에는 사업자등록번호가 있다. 업체 · 분류번호 서버 필터는 없고 품명 필터가 있다. 세부 조회의 물품분류번호 · 물품식별번호는 **모두 8자리**다. 개방표준 입찰공고에는 수요처 · 입찰개시 · 등록마감 · 투찰마감 · 공고 링크가 있으나 **기초금액은 없고**(추정가격 · 배정예산금액만), 낙찰에는 낙찰업체 · 낙찰금액 · 기초금액이 있으나 **공고 링크는 없다.** 개방표준은 범위 제한이 있다: 입찰공고 1개월, 낙찰 개찰일시 **1일**(업무구분코드 필수: 1 물품, 2 외자, 3 공사, 5 용역), 계약 1주일.
- **미확정(실제 호출로 확인 필요):**
  - **물품분류번호 자릿수:** 가이드는 8자리인데 우리가 확정한 `4323320501`은 10자리다. 수집기와 응답 매핑은 아직 없어 지금 당장은 아니지만, 매핑을 그대로 연결하면 현재 필터(정확 일치)가 실제 데이터를 전부 거부한다. 확인 전에는 수집을 만들지 않는다
  - **납품요구:** 어느 가이드에도 납품요구 필드가 없다. 쇼핑몰 납품요구 건이 계약으로 조회되는지(조회되는 것이 단가계약 자체뿐이면 수요기관의 의미가 달라진다) 응답으로 확인해야 한다
  - 날짜 기준: 납품요구일자는 계약체결일자로 대체한다(결정 13). "신규" 판정 날짜는 계약체결일자 + `PPSSrch` + 최근 N일 재조회를 제안했고 승인 대기다(결정 14)
  - 품명 필터의 효과, 하루 계약 · 공고 건수, `numOfRows` 최대값, 낙찰 응답의 투찰업체별 행 구조
- **구현 전에 맞춰야 하는 기존 서술:** 위 `src/g2b/client.ts`는 `G2B_BASE_URL` · `G2B_SERVICE_KEY` 하나만 읽지만 `.env`는 서비스별 변수(`G2B_CONTRACT_*`, `G2B_OPENSTD_*`)로 바뀌었다. `classify()`는 한 레코드에 업체 · 분류번호가 합쳐져 있다고 가정하지만 실제로는 업체(기본 조회)와 분류번호(세부 조회)가 다른 오퍼레이션에 있다. 위 "처리 흐름"의 경쟁사 줄(분류번호 → 업체명 순)도 실제 호출 순서(업체명 → 분류번호)와 다르다. `parseMonitoringConfig`의 분류번호 검증은 10자리 정규식이라 API의 8자리와 맞지 않는다(WO-20261028-06 3절 A). `collectionRange`와 결정 12는 "납품요구일자 범위"를 전제하므로 결정 14에 맞춘다.
- 외부 LLM 호출 기능은 제품에 포함하지 않는다.

## 범위 결정 (사람이 내린 것)
- **SP영업 메일 알림 기능은 범위 밖이다** (2026-10-28 사용자 지시). 구현하지 않는다.
  경쟁사 문서에서는 WO-20261028-02로 해당 부분을 삭제했다(1.2, 시나리오 1, 6장 흐름, 7.1 처리 조건, 10장 요약표, 11장 확인 항목). 7.2는 다른 절 번호 유지를 위해 "(삭제)" 안내만 남겼다. 이후 문서 인용 시 11장의 마지막 항목(엑셀 파일명 및 출력 범위)은 8번이 아니라 7번이다.

## 확장 레시피
### 새 테이블 추가
1. `src/db/index.ts`의 `migrations`에 `{ id: '000N_설명', sql }`를 추가한다(이미 적용된 id는 수정하지 않는다).
2. `migrate`를 쓰는 테스트에 새 스키마를 검증하는 케이스를 추가한다.
3. 위험 신호 "DB 구조 변경"이 켜지므로 검토를 받는다.

### 모니터링 대상 업체 · 확인 대상 제품 추가 (경쟁사)
1. `config/contract-monitoring.json`의 `companies`에 업체를 추가하거나, 기존 업체의 `products`에 8자리 물품식별번호를 추가한다. 상호는 `matchNames`에 나라장터 등록 상호 그대로 넣는다(정확 일치).
2. 등록 상호를 확인하면 `provisional`을 `false`로 바꾼다.
3. `bash scripts/gate.sh`를 돌린다. 설정 검증이 형식 오류와 중복을 막고, `src/filters/contracts.test.ts`의 "실제 설정 파일" 테스트가 업체 수 · 식별번호 수 · 충돌 번호 목록을 고정하고 있으므로 의도한 변경이면 그 숫자도 함께 고친다.
4. 요구사항 문서 3.1 · 9.2의 대상 업체 목록과 어긋나면 `docs` 경로로 문서를 맞춘다.

"새 키워드 추가"(입찰) 같은 확장은 해당 기능이 구현되면 여기에 적는다.

## 함정
요구사항 문서에서 확인된 내부 불일치(구현 전에 사람에게 돌려보낼 목록):
1. (해소됨, WO-20261028-02) 경쟁사 문서의 메일 포함 정보 불일치는 메일 기능 삭제로 사라졌다.
2. 입찰 4.1은 "업무구분 · 추정가격 · 입찰마감일"을 쓰지만 수집 항목은 "기초금액 · 등록마감 · 투찰마감"이다.
3. 입찰 4.2는 "낙찰일자"를 확인한다고 쓰지만 낙찰정보 수집 항목에 낙찰일자가 없다.
4. 입찰 5.4의 추세 예시에 "AI", "개인정보"가 있으나 필터 키워드 15종에는 없다. (필터에 없는 공고는 저장되지 않으므로 추세 집계도 불가)
5. 경쟁사 11장의 미확정 항목(보안SW 분류번호 목록, 업체명 표기, 제품별 식별번호, 중복 방지 키, 수집 시간, 오류 처리)은 구현 전에 확정이 필요하다. 입찰 문서에도 공고↔낙찰 매칭 키 · 수집 시간 · 오류 처리 정의가 없다.
