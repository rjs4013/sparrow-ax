# sparrow-ax 아키텍처

## 개요
스패로우 SP사업팀 · 영업 담당자를 위해 나라장터 데이터를 매일 수집하고 웹 View로 보여 주는 영업 지원 시스템이다.
요구사항은 **별도 View 두 개**(경쟁사 계약·납품 실적, 공공 입찰공고·낙찰)로 정의되어 있다.
**현재는 공통 기반(WO-20261028-03)과 경쟁사 필터 · 응답 파서(WO-20261028-04 · 08)까지 있다.** 경쟁사 계약은 **체결일자 백필 수집 → 저장 → 일/주/월 조회 화면까지 동작한다**(WO-20261028-09, 올해 1~10월 28일 실수집으로 9개사 계약 11건 확인). 하이브리드 수집(매일 등록일시 증분 · 주 1회 체결일자 교차 검증)도 동작한다(WO-20261028-10). **나라장터쇼핑몰의 납품요구(실제 수요기관 · 금액)도 수집 · 저장 · "납품요구" 화면까지 동작한다**(WO-20261028-12, 올해 1~10월 28일 실수집으로 9개사 납품요구 124행). **월 단위 엑셀 내보내기(납품요구 + 계약 두 시트)도 된다**(WO-20261028-13). **입찰 · 낙찰 모니터링은 3단계(입찰공고 + 낙찰정보 수집 · 저장 · "입찰공고" 화면의 대시보드와 두 목록)까지 모두 동작한다**(WO-20261028-14 · 15 · 16, 10월 22~28일 입찰공고 60건 · 10-28 개찰 낙찰정보 3건). **마지막 수집 상태는 "관리" 탭에만 보인다.** 스케줄 등록은 아직 없다.

## 기술 스택 (사람 승인, WO-20261028-03)
Node 24 + TypeScript(`tsc --noEmit`으로 타입 검사, 실행은 Node의 타입 제거), SQLite(`node:sqlite` 내장), Fastify, 테스트는 `node:test`.
엑셀 내보내기용 `exceljs`는 WO-20261028-13에서 설치했다(`npm audit`은 `exceljs` 하위 `uuid`의 중간 등급 2건을 알리지만 게이트 기준인 high 이상은 아니다). 운영 환경은 미정이라 로컬 실행 기준이고 수집은 CLI 명령 + 외부 스케줄러로 붙일 예정이다.
코드는 `import type`과 `.ts` 확장자 import를 쓰고, 열거형 · 네임스페이스 등 타입 제거로 지워지지 않는 문법은 쓰지 않는다(`erasableSyntaxOnly`).

## 주요 진입점
- `src/db/index.ts`: `openDb(path)`는 SQLite를 열고(WAL, 외래키 켬), `migrate(db, list?)`는 미적용 마이그레이션만 id 순으로 트랜잭션 실행한다. 테이블 스키마는 `migrations` 배열에 `{ id: '0001_...', sql }`로 추가한다(현재 `0001_contracts`: `contracts`(고유 키 통합계약번호 + 업체 id)와 `collect_runs`(수집 실행 기록), `0002_run_kind`: `collect_runs`에 `kind`(backfill · daily · verify, 기존 행은 backfill)와 `note` 열, `0003_delivery_requests`: 납품요구 물품 행 `delivery_requests`(고유 키 납품요구번호 + 변경차수 + 물품순번 + 업체 id), 납품요구 수집 실행은 `collect_runs`에 `kind`가 `dlvr_backfill` · `dlvr_daily`인 행으로 남긴다, `0004_delivery_request_name`: 납품요구건명 `dlvr_req_nm` 열 = 요구사항의 "공사명", 이미 저장된 행은 납품요구 백필을 다시 돌려야 채워진다).
- `src/db/contracts.ts`: `upsertContracts`(한 트랜잭션, 같은 키는 갱신), `listContracts`(체결일자 기간 · 업체로 조회, 최근순), `startRun(…, kind)` · `finishRun(…, {…, note})` · `lastRun` · `lastRunByKind`(종류별 최근 실행) · `lastSuccessRun(kind)`(증분의 시작점 계산에 쓴다) · `existingKeys`(교차 검증이 새로 찾은 계약 수를 세는 데 쓴다). 제품 식별번호 · 이름은 JSON 배열 문자열, 불리언은 0/1로 저장한다.
- `src/collect/` (경쟁사 계약 수집): `contracts.ts`의 `collectContracts`는 기간을 달력 월로 나눠 체결일자 검색(`PPSSrch`, 품명 `트랜잭션보안및바이러스보호소프트웨어` 부분 일치 필터, 페이지 999)을 호출하고, 체결일자가 빈 행을 버리고, `corpList`로 9개사를 판정한 뒤, 해당 계약만 세부 조회(페이지 100)해 분류번호 `43233205`와 식별번호를 판정한다. 공동수급이면 업체별로 행을 만든다. `createFetcher`는 호출 수를 세고 상한을 지키며 네트워크 · HTTP 오류를 최대 3회 시도한다(서비스 결과코드 오류는 재시도하지 않는다). `run.ts`의 `runCollection`은 실행 기록으로 감싸고 **끝까지 성공했을 때만** 저장한다(그래서 호출 상한에 걸리면 저장이 0건이다. 기간이 길면 `--from` · `--to`로 쪼개 돌린다. 올해 1~10월은 호출 21회였다). `collectDay`는 **등록일시 하루치**(`getCntrctInfoListThng`, `inqryDiv=1`, `YYYYMMDD0000`~`2359`, 999건 페이지, 서버 품명 필터 없음, 하루 약 4,200건 · 5쪽)를 받아 같은 행 처리(체결일자 빈 행 폐기 → 업체 → 세부 조회 → 분류번호)를 한다. `runDaily`(**매일 증분**)는 마지막 성공한 `daily` 기록의 다음 날(없으면 가장 최근 성공한 백필이 시작된 한국 날짜, 둘 다 없으면 "백필 먼저" 오류)부터 어제까지를 **하루씩** 받고, 하루가 끝날 때마다 그 날 결과를 저장하고 `daily` 실행 기록을 한 행 남긴다. 중간에 실패하면 거기서 멈추고 다음 실행이 실패한 날부터 이어 간다(`--from`으로 시작일을 직접 줄 수도 있다). `runVerify`(**교차 검증**)는 최근 N일(기본 14)을 체결일자 방식으로 다시 받아 저장하고, DB에 없던 계약 수를 `note`("새로 찾은 계약 N건")에 남긴다. 메모는 "새로 찾은 계약 N건 · 그중 증분이 놓친 것 M건"이고, **M(등록일이 증분의 마지막 성공일 이하인데 없던 계약)이 0이 아니면 증분이 무언가 놓쳤다는 신호**다. 등록일이 아직 증분 차례 전인 계약은 N에만 들어가고 M에는 들어가지 않는다(증분 성공 기록이 없으면 M은 판정 불가로 표시). `--days`는 8 이상이어야 한다(등록 지연 관측 최대 7일). 증분은 받을 날이 없으면 실행 기록을 남기지 않으므로 화면의 "매일 증분" 시각이 어제 이후로 갱신되지 않으면 스케줄이 멈춘 것이다. 몇 달 밀린 뒤라면 `--max-calls`를 올려 한 번에 받거나(일일 한도 1000회 안에서) 여러 번 나눠 실행한다(진행은 날짜 단위로 보존된다). `main.ts`는 명령이다: `npm run collect -- --mode backfill --from 2026-01-01 --to 2026-10-28`(기본 모드, 상한 40, 기본 기간 올해 1월 1일~어제) · `--mode daily [--from 날짜]`(상한 80) · `--mode verify [--days 14]`(상한 40). 모두 같은 구간을 다시 돌려도 안전하다. `.env`의 `G2B_CONTRACT_*`가 필요하다. **스케줄은 만들지 않았다**(운영 환경 미정): 사람이 daily는 매일 새벽, verify는 주 1회로 작업 스케줄러에 건다.
- `src/g2b/client.ts`: `loadG2bConfig(env, service)`는 서비스별 변수(`service`는 `CONTRACT` · `OPENSTD` · `SHOPPING`이고 **`OPENSTD`만 서비스키를 대문자 `ServiceKey` 이름으로 보낸다**(가이드 이름, 실호출 확인), 예를 들어 `CONTRACT`면 `G2B_CONTRACT_SERVICE_KEY` · `G2B_CONTRACT_BASE_URL`, `OPENSTD`면 `G2B_OPENSTD_*`)를 읽고 요청주소가 https가 아니면 거부하며(키가 쿼리스트링으로 가므로), `createG2bClient(config, fetch?)`는 `buildUrl` · `get`을 제공한다. 서비스키는 오류 메시지에 남기지 않는다(호출 실패 · JSON 파싱 오류는 원문 · 인코딩 형태 모두 마스킹, 응답 오류에는 키 없는 URL 사용). 빈 키로는 클라이언트를 만들 수 없다. 포털의 Decoding(원문) 키를 쓴다. 기본 호출은 리다이렉트를 따르지 않고(`redirect: 'error'`) 60초 제한 시간을 둔다(월 범위 조회가 10~24초 걸린다). 재시도 · 호출 상한은 클라이언트가 아니라 `src/collect/contracts.ts`의 `createFetcher`가 맡는다.
- `src/g2b/response.ts` (나라장터 OpenAPI 응답 파서, 순수 함수 — 계약정보 · 쇼핑몰 공용, `items`가 배열이거나 `{item: …}`로 싸여 와도 읽는다): `parsePage(raw)`는 `{items, totalCount, pageNo, numOfRows}`를 돌려준다. **HTTP 200으로 오는 오류 래퍼(`…ResponseError`)와 `resultCode`가 `00`이 아닌 응답은 `G2bResponseError`(`code` = 결과코드)로 던지고**, 응답 모양이 예상과 다르면 `code`가 `null`인 같은 오류를 던진다(빈 결과로 읽지 않는다). 결과가 없을 때 `items` 키가 없는 것은 빈 배열로 읽는다. 항목 키는 소문자로 보관하고 `field(row, 이름)`이 대소문자 무시로 읽는다. `parseCorpList` · `parseDemanderList`는 `[순번^…]` 목록을 칸 수까지 검사해 풀고(상호 안의 대괄호 허용) 대표자 · 담당자 · 전화번호는 버린다. `isPlaceholderDemander`는 "각 수요기관"(`ZZ99999`)을 실제 구매처가 아닌 자리표시자로 판정한다. 저장해 둔 실제 응답 7,863행으로 파싱을 확인했다(이 응답 파일은 저장소에 없다).
- `src/db/deliveries.ts`: `upsertDeliveries`(한 트랜잭션, 같은 키는 갱신), `listDeliveries`(접수일자 기간 · 업체로 조회, 최근순). **변경 차수가 여럿이면 저장은 모두 하고 조회는 (납품요구번호, 물품순번, 업체)별로 한 행만 돌려주되, 기간은 최초 접수일자로 판정하고 값은 가장 큰 변경 차수의 것이다**(변경본 접수일자가 다른 달이어도 원래 기간에 남는다). 실측 사례 1건: 변경 1차가 수량 0 · 금액 0 · 증감 음수 · 접수일자 하루 뒤인 취소였다(화면에 "취소(수량 0)" 표시).
- `src/collect/deliveries.ts`: `collectDeliveries`는 접수일자 구간을 달력 월로 나눠 납품요구 상세(`getDlvrReqDtlInfoList`, `inqryDiv=1`, 품명 필터, 999행/쪽)를 받고, 업체(상호 정확 일치) → 분류번호 8자리 → 식별번호 표시(목록 밖이어도 저장) 순으로 저장 행을 만든다. `run.ts`의 `runDeliveryBackfill`은 끝까지 성공했을 때만 저장한다(`dlvr_backfill` 기록). `runDeliveryDaily`는 `dlvr_daily`(없으면 `dlvr_backfill`) 성공 기록의 마지막 날 다음 날부터 어제까지에 **최근 3일을 더해**(접수일자 등록 지연을 모르므로) 한 번에 받는다(`dlvr_daily` 기록, 받을 날이 없으면 호출하지 않는다). 명령: `npm run collect -- --mode dlvr-backfill --from … --to …`(상한 40) · `--mode dlvr-daily`(상한 20). `.env`의 `G2B_SHOPPING_*`가 필요하다.
- `src/filters/bids.ts` + `config/bid-monitoring.json`: 입찰공고 공고명 필터 키워드 15종(요구사항 2.3). `matchKeywords(title, keywords)`는 **대소문자를 무시한 단순 포함**으로 걸린 키워드를 설정 순서대로 돌려준다(사람 결정). 단어 경계를 보지 않아 "Developer" · "Apple" · "application"도 걸리는 잡음이 있다(실측: 평일 하루 약 1,600~2,100건 중 7~17건 적중, "솔루션" · "컨설팅"이 대부분).
- `src/db/bids.ts`: `upsertBids`(한 트랜잭션, (공고번호, 차수) 고유) · `listBids`(공고일자 기간, 최근순). 담당자 이름 · 전화 · 이메일은 저장하지 않는다. 마이그레이션 `0005_bid_notices`.

(구현 상태: **백필 경로는 구현됨** — 체결일자 월 단위 검색(품명 필터) → 체결일자 빈 행 폐기 → 업체명 판정(기본 조회의 `corpList`) → 세부 조회로 분류번호 → 식별번호 표시 → 저장 → 웹 조회. 업체는 기본 조회에, 분류번호는 세부 조회에 있어 실제 판정 순서는 업체명 → 분류번호다. **결정 14의 하이브리드도 구현됨(WO-20261028-10)** — 매일 등록일시 증분(하루 단위 저장 · 재개)과 주 1회 체결일자 교차 검증. **엑셀 내보내기도 구현됨(WO-20261028-13)**(납품요구 + 계약 두 시트, 선택한 달 전체). **아직 없음:** 스케줄 등록. 삭제 · 재분류는 upsert라 반영되지 않는다)
- 납품요구(쇼핑몰): 접수일자 월 단위 백필(품명 필터) → 업체 정확 일치 → 분류번호 → 식별번호 표시 → 저장(변경 차수별) → 웹 "납품요구" 화면(가장 큰 변경 차수만) / 매일: 마지막 성공일 다음 날~어제 + 최근 3일 재조회. 계약정보와는 번호로 연결하지 않는다(독립 원천).
- 입찰공고(구현됨, WO-20261028-14): 전일자(입찰공고일시 하루 단위) 조회 → 공고명 키워드 필터(대소문자 무시 포함) → 저장((공고번호, 차수)별) → 웹 "입찰공고" 화면(공고 링크로 나라장터 원문 이동).
- 낙찰정보(구현됨, WO-20261028-15): 개찰일 하루 단위(업무구분 물품 · 용역) → 쪽마다 공고명 키워드 필터(입찰공고와 같은 15종) → 투찰업체 행을 공고 하나로 묶어 낙찰자 추출 → 저장 → 웹에서 입찰공고와 (공고번호, 차수)로 연결(없으면 단독). **최종 낙찰자는 개찰 며칠 뒤에 채워진다**(실측: 용역 개찰 2일 뒤 32%, 9일 뒤 57%)여서 개찰 다음 날 받은 결과에는 "낙찰자 미확정"이 많고, `--from`으로 그 날을 다시 받으면 갱신된다(이미 정해진 낙찰자는 지워지지 않는다). 낙찰자 보완용으로 개방표준 **계약정보**(`getDataSetOpnStdCntrctInfo`)를 쓸 수 있으나 이번에는 쓰지 않았다(아래 실측). 대시보드 · 키워드 추세(필터 키워드 15종만, 사람 결정)는 WO-20261028-16에서 구현했다(저장된 데이터를 집계할 뿐 API를 부르지 않는다).

  - **실측으로 확인된 제약(WO-20261028-07):** 페이지 크기는 계약 `PPSSrch` 999, 세부 조회 100(이상 미시험), 입찰공고 500, 낙찰 500이다. **계약 `PPSSrch`의 기간은 3개월 범위가 거절되고(결과코드 07 "입력범위값 초과 에러") 28일은 허용된다**(월 단위로 나눠야 하며 31일은 미시험). 오류 응답은 HTTP 200이고 구조가 `{"nkoneps.com.response.ResponseError": {"header": …}}`로 정상 응답과 달라 **파서가 이 래퍼를 인식해야 한다**(WO-20261028-08에서 `src/g2b/response.ts`로 구현). 서비스키는 `ServiceKey`와 `serviceKey` 모두 통한다(계약정보). 품명 필터는 부분 일치이고 `chgDt`는 지금까지 받은 3987건에서 한 번도 채워지지 않았다
  - 품명 필터의 효과, 하루 계약 · 공고 건수, `numOfRows` 최대값, 낙찰 응답의 투찰업체별 행 구조
- **구현 전에 맞춰야 하는 기존 서술(WO-20261028-08에서 서비스별 설정 · 판정 분리 · 8자리는 해소):** `collectionRange`(마지막 성공일 다음 날 ~ 어제)는 이제 매일 증분(등록일시)의 범위 계산에 쓰인다. 다만 주석과 결정 12의 서술은 아직 "납품요구일자 범위"라고 되어 있어 의미(등록일시 기준)에 맞춰 정리해야 한다.
- 외부 LLM 호출 기능은 제품에 포함하지 않는다.

## 확장 레시피
### 새 테이블 추가
1. `src/db/index.ts`의 `migrations`에 `{ id: '000N_설명', sql }`를 추가한다(이미 적용된 id는 수정하지 않는다).
2. `migrate`를 쓰는 테스트에 새 스키마를 검증하는 케이스를 추가한다.
3. 위험 신호 "DB 구조 변경"이 켜지므로 검토를 받는다.

### 모니터링 대상 업체 · 확인 대상 제품 추가 (경쟁사)
1. `config/contract-monitoring.json`의 `companies`에 업체를 추가하거나, 기존 업체의 `products`에 8자리 물품식별번호를 추가한다. 상호는 `matchNames`에 나라장터 등록 상호 그대로 넣는다(정확 일치).
2. 등록 상호를 확인하면 `provisional`을 `false`로 바꾼다.
3. `bash scripts/gate.sh`를 돌린다. 설정 검증이 형식 오류와 중복을 막고, `src/filters/contracts.test.ts`의 "실제 설정 파일" 테스트가 업체 수 · 식별번호 수 · 충돌 번호 목록을 고정하고 있으므로 의도한 변경이면 그 숫자도 함께 고친다.
4. 요구사항 문서 3.1 · 9.2의 대상 업체 목록과 어긋나면 `docs` 경로로 문서를 맞춘다.

"새 키워드 추가"(입찰) 같은 확장은 해당 기능이 구현되면 여기에 적는다.
